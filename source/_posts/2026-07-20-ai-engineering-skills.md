# AI 工程师的技能手册：如何用一套可复用的命令规范 AI 辅助开发

## 为什么需要"技能手册"

用 AI 写代码已经不是什么新鲜事，但很多人（包括我）都遇到过同样的问题：AI 很聪明，但**每次对话都是从零开始**。同样的需求，今天和昨天问出来的代码质量不一样；同一个项目，换个会话就忘记了你约定好的术语和架构决策。

AI 工程师技能手册的答案是把 AI 辅助开发**流程化、命令化、可复用**——就像给 AI 装了一套标准化的"操作手册"，每个场景对应一个命令，命令背后是沉淀好的方法论。这套手册基于 Matt Pocock Skills（GitHub 19 万+ stars），我自己在 LifeOS 项目中实践了一个月，这篇文章是完整的整理和思考。

## 快速开始：每个新项目只需一次

```
/setup-matt-pocock-skills
```

跑一次，配置三件事：

- **Issue Tracker**：GitHub / Linear / 本地文件
- **Triage Labels**：根据团队习惯设置
- **文档存储位置**：项目根目录

之后所有技能命令就能在这个项目里用了。

## 四大核心工作流

### 1. 需求澄清（最重要！）

```bash
# 开始任何新功能前，先用这个
/grill-with-docs
```

这是整个手册里最重要的一个命令。AI 开发最常见的翻车点不是代码写得差，而是**需求没搞清楚就开始写**。`/grill-with-docs` 会连环追问直到需求完全清晰，并且自动做两件事：

- 建立 `CONTEXT.md` 领域术语表——AI 以后都用你定义好的词说话，不再自己发明术语
- 把关键决策记录到 `docs/adr/`（Architecture Decision Records）——以后任何人（包括 AI）都能追溯"当初为什么这么设计"

**输出**：`CONTEXT.md`（术语表）+ `docs/adr/`（决策记录）

### 2. 测试驱动开发

```bash
# 写代码时
/tdd
```

经典的红 → 绿 → 重构循环，让 AI 严格按步骤来：

1. 先写一个失败的测试
2. 写最少的代码让它通过
3. 重构代码保持测试通过

对 AI 来说 TDD 尤其重要——**测试就是给 AI 的"验收标准"**。没有测试，AI 可能觉得自己写完了，但你无法验证它真的对。

### 3. 代码审查

```bash
# 写完后
/code-review
```

双维度审查：

- **Standards**：是否遵循项目编码标准
- **Spec**：是否忠实实现了需求

这两个维度缺一不可——代码写得再优雅，没实现需求是白搭；需求实现了，风格和项目不一致也不好维护。

### 4. 架构维护

```bash
# 每隔几天跑一次
/improve-codebase-architecture
```

AI 辅助开发有个隐藏问题：**代码生成速度远超架构演进速度**。功能加得快，模块边界烂得也快。这个命令会扫描代码库的架构问题、生成可视化 HTML 报告、帮你逐步优化。

## 完整技能清单

### 工程类（Engineering）

| 命令 | 触发场景 | 作用 |
|------|----------|------|
| `/grill-with-docs` | 开始新功能前 | 需求澄清 + 建立领域模型 |
| `/tdd` | 写代码时 | 测试驱动开发 |
| `/implement` | 有 spec 后 | 根据 spec 实现，自动调用 TDD |
| `/code-review` | 写完代码后 | 双维度代码审查 |
| `/to-spec` | 对话结束后 | 把对话变成 spec |
| `/to-tickets` | 有计划后 | 拆分成可追踪 ticket |
| `/diagnosing-bugs` | 调试时 | 结构化调试循环 |
| `/improve-codebase-architecture` | 代码变乱时 | 架构扫描 + 优化报告 |
| `/wayfinder` | 大型任务 | 生成 investigation tickets |
| `/prototype` | 设计决策时 | 快速原型验证 |
| `/research` | 技术选型时 | 后台调研 + 生成报告 |
| `/triage` | 处理 issue 时 | Issue 分类流转 |
| `/ask-matt` | 不知道用哪个 | 技能路由器 |

### 生产力类（Productivity）

| 命令 | 触发场景 | 作用 |
|------|----------|------|
| `/grill-me` | 非代码需求 | 连环追问澄清 |
| `/handoff` | 换 agent 时 | 生成交接文档 |
| `/teach` | 学习新概念 | 多轮教学模式 |

## 最佳实践组合

这套技能最值钱的地方，是**组合使用**：

### 每次开发新功能

```
1. /grill-with-docs    # 先澄清需求，建立术语
2. /to-tickets         # 拆分成 ticket
3. /implement          # 逐个实现
4. /code-review        # 审查
```

### 代码变乱时

```
/improve-codebase-architecture
```

### 遇到难 bug

```
/diagnosing-bugs
```

### 大型任务（超过一个 session）

```
/wayfinder
```

## 关键文件设计

整套体系的灵魂是三个文件/目录：

- `CONTEXT.md` - 项目术语表，AI 必读——**统一语言是协作的地基**
- `docs/adr/` - 架构决策记录——**让每个设计决策都有据可查**
- `.opencode/skills/` - 技能配置——**命令背后的方法论沉淀**

## 我的实践感受

用了一个月，最直观的三个变化：

1. **"重新开始"的成本大幅下降**。之前换会话做同一个项目，AI 会忘掉上下文；现在 `CONTEXT.md` + ADR 让每个新会话都能快速恢复"记忆"。
2. **需求澄清带来的收益被严重低估**。以前我习惯"直接让 AI 写"，结果经常返工；`/grill-with-docs` 的连环追问确实烦，但烦在开始，省在结尾。
3. **TDD 让 AI 代码"可验证"**。不是信任 AI 写得好，而是让测试告诉我它写得好不好。

## 补充：BrowserMCP 配置

这套体系里还配了浏览器自动化能力（BrowserMCP），用于 Web 导航、表单填写、数据提取和自动化测试。在 `opencode.json` 的 `mcp` 配置中加入即可启用，配合技能命令使用，AI 就能在"写代码"和"操作浏览器验证"之间无缝切换。
